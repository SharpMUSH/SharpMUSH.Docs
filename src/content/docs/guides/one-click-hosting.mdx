This page takes you from nothing to a public game with a web portal and telnet, on a server you rent
by the month. You fill in a short form, or paste one block of text, and an installer does the rest:
it installs Docker, starts SharpMUSH, gets an HTTPS certificate, and keeps the game locked to you
until you have claimed the admin account.

![Players' browsers reach Caddy over HTTPS, directly or through a Cloudflare Tunnel; Caddy passes the portal to the game server and the web terminal to the connection server. MUD clients reach the connection server on telnet port 4201. NATS, the renderer and the game server run on the same server, with the world on its disk.](../../../assets/guide/one-click-hosting.svg)

## Pick a host

| Host | How you launch | Rough monthly cost |
|---|---|---|
| Any VPS provider (DigitalOcean, Hetzner, Vultr, Linode, OVH, ...) | Paste the setup text into the server's user data box | $12 for 2 GB, $24 for 4 GB on most; Hetzner is cheaper |
| Akamai / Linode | Fill in the SharpMUSH StackScript form | $12 for 2 GB, $24 for 4 GB |
| Fly.io | Run one command from your computer | about $20 for the three machines ($11 as one app), $1.50 for storage, and $2 for an IPv4 telnet address if you add one |
| Railway | Create three services in Railway's dashboard | billed by use on top of Railway's $5 Hobby plan; see railway.com/pricing |

All of them need a server with **at least 2 GB of memory**; 4 GB is comfortable. Choose Ubuntu 24.04
(or later) or Debian 12 when the host asks for an operating system.

A VPS is the simpler choice: the game gets the whole server, updates itself, and an engine update
does not disconnect your players. On Fly.io and Railway nothing updates until you do it. There too,
updating the game server or the renderer keeps everyone connected; only the edge, which holds the
connections, disconnects everyone when it updates. A Fly game launched as one app (`--single`)
disconnects everyone on every update. See [Update your game](#update-your-game).

<Aside type="caution">
SharpMUSH has no release yet. Every route here runs the `dev` images, built from each change merged
into SharpMUSH after its tests pass. Expect changes, and keep backups.
</Aside>

## Decide on an address

The installer needs to know what address your portal will have. You have three choices.

- **No domain.** Leave the domain empty and the game starts at `<your-server-ip>.sslip.io`, which
  works with no DNS set up at all. It is the quickest way to try things, but the certificate service
  limits how many sslip.io certificates it issues each week across everyone using it, so it can fail
  at busy times. Move to your own domain once you have one.
- **Your own domain.** For example `mush.example.com`. Before you launch, add an **A record** for it
  pointing at the server's IP address. On most hosts you only learn the address once the server
  exists, so either reserve an address first or add the record straight after creating the server.
  The certificate arrives as soon as the record does.
- **A domain on Cloudflare.** Give the installer a Cloudflare API token and it sets everything up:
  a tunnel for the portal, so your server opens no web ports, and a `telnet.<your-domain>` record for
  MUD clients. See [Make a Cloudflare API token](#make-a-cloudflare-api-token).

## Launch on any VPS

<Steps>

1. Start creating a server with your host. Pick Ubuntu 24.04 and a plan with 2 GB of memory or more.

2. Find the field for **user data**. Hosts give it different names: look for *user data*,
   *cloud-init*, *cloud config* or *initialization script*, often under advanced options.

3. Paste this text into it, and fill in the lines you want. Every line may stay empty.

   ```yaml
   #cloud-config
   write_files:
     - path: /root/sharpmush-answers.env
       permissions: "0600"
       content: |
         # The portal's domain, e.g. mush.example.com. Empty: the game starts on <ip>.sslip.io.
         SHARPMUSH_DOMAIN=
         # Optional, with a domain on Cloudflare: sets up the tunnel and DNS for you.
         CLOUDFLARE_API_TOKEN=
         # Optional: an existing tunnel's token instead (point its hostname at http://caddy:80).
         CLOUDFLARE_TUNNEL_TOKEN=
         SHARPMUSH_SOURCE_REF=main

   runcmd:
     - - bash
       - -c
       - |
         set -euo pipefail
         set -a; . /root/sharpmush-answers.env; set +a
         curl -fsSL "https://raw.githubusercontent.com/SharpMUSH/SharpMUSH/${SHARPMUSH_SOURCE_REF:-main}/deploy/oneclick/install.sh" -o /root/sharpmush-install.sh
         bash /root/sharpmush-install.sh 2>&1 | tee /var/log/sharpmush-install.log
         shred -u /root/sharpmush-answers.env /root/sharpmush-install.sh
   ```

4. Create the server and wait three to five minutes while it installs.

5. Log in over SSH (`ssh root@<your-server-ip>`). The welcome message shows your game's addresses and
   your **setup link**. Carry on with [Finish setup](#finish-setup).

</Steps>

<Aside>
Already have a server? Log in over SSH and run the installer directly. It asks no questions and uses
`<ip>.sslip.io`; run `sharpmush-configure` afterwards to give it a domain.

```bash
curl -fsSL https://raw.githubusercontent.com/SharpMUSH/SharpMUSH/main/deploy/oneclick/install.sh | sudo bash
```
</Aside>

## Launch on Akamai / Linode

<Steps>

1. In Linode's Cloud Manager, open **StackScripts**, then **Create StackScript**. Name it
   SharpMUSH, tick Ubuntu 24.04 and Debian 12 as target images, and paste this script:

   ```bash
   #!/bin/bash
   # <UDF name="SHARPMUSH_DOMAIN" label="Domain for the web portal" example="mush.example.com. Leave empty to start on <ip>.sslip.io." default="" />
   # <UDF name="CLOUDFLARE_API_TOKEN" label="Cloudflare API token (optional)" default="" />
   # <UDF name="CLOUDFLARE_TUNNEL_TOKEN" label="Existing Cloudflare tunnel token (optional)" default="" />
   # <UDF name="SHARPMUSH_SOURCE_REF" label="SharpMUSH installer version (git ref)" default="main" />
   set -euo pipefail
   exec > >(tee -a /var/log/stackscript.log) 2>&1
   export SHARPMUSH_DOMAIN CLOUDFLARE_API_TOKEN CLOUDFLARE_TUNNEL_TOKEN SHARPMUSH_SOURCE_REF
   curl -fsSL "https://raw.githubusercontent.com/SharpMUSH/SharpMUSH/${SHARPMUSH_SOURCE_REF:-main}/deploy/oneclick/install.sh" \
     -o /root/sharpmush-install.sh
   bash /root/sharpmush-install.sh
   rm -f /root/sharpmush-install.sh
   ```

2. Save it and choose **Deploy New Linode**. The form now has a field for each line above: fill in
   the ones you want.

3. Pick a region, a **Shared CPU** plan with 4 GB (2 GB works), a root password, and create the Linode.

4. After three to five minutes, log in over SSH. The welcome message has your setup link. Carry on
   with [Finish setup](#finish-setup). If it is not there yet, the install is still running:
   `tail -f /var/log/stackscript.log` shows how far it has got.

</Steps>

## Launch on Fly.io

You need a Fly.io account and [flyctl](https://fly.io/docs/flyctl/install/) on your own computer.
Fly runs the ready-built `sharpmush/sharpmush-allinone` image, so there is nothing to download or build.

The game runs as three Fly apps on a private network of their own:

| App | Runs | Public |
|---|---|---|
| `my-game` | the edge: the web front, the message bus and every player's connection | portal, telnet |
| `my-game-server` | the game server, with the world on its volume | no |
| `my-game-renderer` | the renderer, which formats output for each client | no |

Split this way, updating the game server or the renderer drops nobody.

<Steps>

1. Sign in.

   ```bash
   fly auth login
   ```

2. Make a folder for the game's settings and launch from it. Pick an app name (it becomes
   `<name>.fly.dev`) and a [region](https://fly.io/docs/reference/regions/) near your players.

   ```bash
   mkdir my-game && cd my-game
   curl -fsSL https://raw.githubusercontent.com/SharpMUSH/SharpMUSH/main/deploy/fly/launch.sh | bash -s -- my-game iad
   ```

   On Windows, in PowerShell:

   ```powershell
   mkdir my-game; cd my-game
   & ([scriptblock]::Create((irm https://raw.githubusercontent.com/SharpMUSH/SharpMUSH/main/deploy/fly/launch.ps1))) my-game iad
   ```

   This saves each app's settings beside you as `my-game.edge.fly.toml`, `my-game.server.fly.toml`
   and `my-game.renderer.fly.toml`. It creates the three apps, a 1 GB volume for the edge, a 10 GB
   volume for the world and two free addresses for the edge, IPv6 and a shared IPv4. Then it
   starts the edge, the server and the renderer, in that order. Keep the folder: you update the
   game from it.

3. Find your setup link in the log, and carry on with [Finish setup](#finish-setup).

   ```bash
   fly logs --app my-game --no-tail | grep setup_code
   ```

   In PowerShell, use `Select-String setup_code` in place of `grep setup_code`.

   Players connect their MUD clients to `my-game.fly.dev`, port 4201.

</Steps>

<Aside>
Fly's shared IPv4 address carries only web traffic. The portal and the web terminal reach everyone,
but telnet answers over IPv6 alone, so a player whose network has no IPv6 cannot connect a MUD
client. To fix that, run the launch script again with `--dedicated-ipv4` (`-DedicatedIPv4` in
PowerShell). It adds an IPv4 address of the game's own, which Fly charges $2 a month for.
</Aside>

To use your own domain on Fly, run `fly certs add mush.example.com --app my-game`, add the DNS records
it asks for, set `SHARPMUSH_DOMAIN` in `my-game.edge.fly.toml`, and deploy the edge again:
`fly deploy --app my-game --config my-game.edge.fly.toml`. That drops everyone connected.

To run the whole game as one app, add `--single` (`-Single` in PowerShell) the first time you
launch. It costs about half as much, roughly $11 a month in place of $20, but every update drops
everyone connected. Its settings are in `my-game.fly.toml`. A game keeps the layout it was launched
with; moving it to the other means launching a new game and restoring an `@backup` copy there.

## Launch on Railway

Railway runs the same ready-built image as Fly, as three services in one project: `edge`,
`server` and `renderer`. You need a Railway account on the Hobby plan or above.

<Steps>

1. Create a project. Add three services, each with **Create** → **Docker Image** and
   `sharpmush/sharpmush-allinone:dev`, and name them `edge`, `server` and `renderer`. The names
   matter: the variables below use them to find each other.

2. Give each service its **Variables**:

   | Service | Variable | Value |
   |---|---|---|
   | `edge` | `SHARPMUSH_ROLE` | `edge` |
   | | `PORT` | `8000` |
   | | `SHARPMUSH_TRUSTED_PROXIES` | `0.0.0.0/0 ::/0` |
   | | `SHARPMUSH_SERVER_ADDRESS` | `${{server.RAILWAY_PRIVATE_DOMAIN}}:8080` |
   | | `Rendering__Address` | `http://${{renderer.RAILWAY_PRIVATE_DOMAIN}}:5100` |
   | `server` | `SHARPMUSH_ROLE` | `server` |
   | | `SHARPMUSH_NATS_URL` | `nats://${{edge.RAILWAY_PRIVATE_DOMAIN}}:4222` |
   | `renderer` | `SHARPMUSH_ROLE` | `renderer` |
   | | `Rendering__Address` | `http://${{RAILWAY_PRIVATE_DOMAIN}}:5100` |

   Type the `${{...}}` values as they are: Railway fills in each service's private address.
   `SHARPMUSH_TRUSTED_PROXIES` lets the game believe Railway's front door about who is visiting.
   Nothing but that front door can reach the edge's web port, so it trusts only Railway.

3. Add two volumes: right-click an empty spot on the project canvas, or press Ctrl+K (⌘K on a Mac)
   and search for "volume". Attach one to `edge` and one to `server`, both mounted at `/data`. The
   world lives on the server's.

4. In the `edge` service's **Settings**, under **Networking**: generate a domain on port `8000` for
   the portal, and add a **TCP Proxy** on port `4201` for telnet. Under **Deploy**, set the
   healthcheck path to `/health`. Give `server` and `renderer` no public networking. On all three,
   leave automatic image updates off.

5. Deploy. The edge's deploy log shows your setup link and the telnet address Railway picked for
   you, such as `shortline.proxy.rlwy.net` port `31457`. Carry on with
   [Finish setup](#finish-setup).

</Steps>

## Finish setup

Until you finish this step, your game is locked: the portal answers only a browser that has opened
your setup link, and telnet answers only on the server itself. Anyone else who finds the address sees
a short page saying the server is waiting for its owner.

<Steps>

1. Open the setup link from the welcome message (or the edge's log on Fly or Railway). It looks like
   `https://mush.example.com/?setup_code=4f1c...`, and takes you to the setup page.

2. Choose the administrator's name and password. This account is linked to God (`#1`).

3. Work through the rest of the setup wizard: import an existing database if you have one, then pick
   the packages you want.

</Steps>

Within 15 seconds of the admin account being claimed, the lock lifts: the portal opens to everyone
and telnet starts answering on port 4201. Give players the portal address and, for MUD clients, the
telnet address from the welcome message.

## Make a Cloudflare API token

<Steps>

1. In the Cloudflare dashboard, open **My Profile**, then **API Tokens**, then **Create Token**,
   and choose **Create Custom Token**.

2. Give it these three permissions:

   | | | |
   |---|---|---|
   | Account | Cloudflare Tunnel | Edit |
   | Zone | DNS | Edit |
   | Zone | Zone | Read |

3. Under **Account Resources**, choose your account. Under **Zone Resources**, choose
   **Specific zone** and your domain, so the token can change DNS for that domain only.

4. Create the token, copy it into the `CLOUDFLARE_API_TOKEN` field, and put your domain in
   `SHARPMUSH_DOMAIN`.

</Steps>

The installer uses the token once and does not store it. Your host keeps a copy of what you typed
into the launch form, so revoke the token in the same dashboard page once the game is up.

## Change things later

Log in over SSH and run:

```bash
sharpmush-configure
```

It asks again for the domain and the Cloudflare tokens, with the current answer in brackets. Press
Enter to keep an answer, type a new one, or type `none` to clear it. Backups are set as in
[Turn on backups](#turn-on-backups). Use it to move from sslip.io to your own domain, to put the
game behind Cloudflare, or to take it out again.

The game lives in `/opt/sharpmush` and starts on boot.

## Update your game

Take a backup before any update you do by hand (`@backup` in the game, as a wizard). A world that a
newer server has upgraded cannot be opened by an older one, so going back needs that copy.

### On a VPS

The game server and the renderer update themselves. A few minutes after a new version is published,
they restart on it. Players stay connected: they see a restart notice, and what they type while the
game is down usually runs once it is back.

The connection server does not update itself, because it holds every player's connection and
replacing it disconnects everyone. Update it when you are ready to drop players, after telling them:

```bash
cd /opt/sharpmush
docker compose pull socketserver
docker compose up -d socketserver
```

Restarting the server, or the `sharpmush` service, also pulls the newest version of everything,
connection server included.

### On Fly.io

Nothing updates on its own. From the folder you launched from, run the launch command again. It
updates the game server and the renderer, and players stay connected through both restarts.

The edge is left as it is, because updating it disconnects everyone. When you are ready to drop
players, after telling them, add `--update-edge` (`-UpdateEdge` in PowerShell) to the launch
command, or update the edge alone:

```bash
fly deploy --app my-game --config my-game.edge.fly.toml
```

A game launched with `--single` restarts as a whole on every update and disconnects everyone, so
pick a quiet time and announce it:

```bash
fly deploy --app my-game --config my-game.fly.toml
```

### On Railway

Nothing updates on its own while automatic image updates stay off. When a service's settings offer
an update for the image, apply it:

- `server` and `renderer`: whenever you like. Players stay connected through the restart.
- `edge`: every update disconnects everyone, so pick a quiet time and announce it.

## Turn on backups

The game copies the world to the server's own disk every six hours. For copies that survive losing
the server, log in as root and run `sharpmush-configure` with the backup settings set. They are not
in the launch forms, because your host keeps what you type there for as long as the server exists.

```bash
RESTIC_REPOSITORY=b2:my-bucket:sharpmush RESTIC_PASSWORD='a long password' \
  B2_ACCOUNT_ID=... B2_ACCOUNT_KEY=... sharpmush-configure
```

| Field | Backblaze B2 | Cloudflare R2 or S3 |
|---|---|---|
| `RESTIC_REPOSITORY` | `b2:<bucket>:sharpmush` | `s3:https://<account-id>.r2.cloudflarestorage.com/<bucket>` |
| `RESTIC_PASSWORD` | a long password you keep safe | the same |
| keys | `B2_ACCOUNT_ID`, `B2_ACCOUNT_KEY` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` |

<Aside type="caution">
Without the backup password the backups cannot be read. Store it in a password manager.
</Aside>

Create the repository once, before the first nightly run at 03:30:

```bash
cd /opt/sharpmush && docker compose run --rm backup restic init
```

[Backups](/guides/deployment#backups) covers checking and restoring them.

## When something goes wrong

| What you see | What to do |
|---|---|
| No welcome message with a setup link | The install is still running or failed. Read `/var/log/sharpmush-install.log` (`/var/log/stackscript.log` on Linode). |
| The browser warns about the certificate | The domain's A record does not point at the server yet, or sslip.io's weekly certificate limit is used up. Check the record, or give the game your own domain with `sharpmush-configure`. |
| "Waiting for its owner to finish setup" | That browser has not opened the setup link. Open it from the welcome message. |
| Telnet connects nowhere | Setup is not finished yet; telnet opens once it is. |
| Anything else | `cd /opt/sharpmush && docker compose ps` shows what is running, and `docker compose logs sharpmush-server` shows the game's log. |
