---
title: Your first softcode command
description: Create, change, and review a small softcode command as a game administrator.
---

This guide is for a new game administrator learning to write and maintain softcode. You will create one small code object, give it a `+hello` command, change it, and test it as both staff and an ordinary player.

The examples show a character named Alice. Lines starting with `>` are what you type; the lines after them are what the game answers.

## Start with a safe place to work

Use your own development game or an approved staff sandbox. You need a character allowed to create a thing and edit its attributes, with enough building quota and currency for your game's configuration. If creation is refused, have an administrator check your effective roles and command restrictions before continuing. Do not change permissions on a public demonstration game to follow this guide. See [roles](/reference/sharpmush-help/roles/) and [command restrictions](/reference/sharpmush-help/command/).

You do not need to build a room. The first command will live on a thing you carry. A carried object's commands are available to its carrier; placing it in a room makes them available to people in that room. Keep this experiment out of the Master Room, where commands become game-wide. See [$-commands](/reference/sharpmush-help/commands/).

Keep a plain-text file beside the game for your code and test notes. Record the server version, character, and object dbref. A dbref such as `#24` identifies one object in this database; it is not a portable identifier between games.

## Create the object

```
> @create Hello Tutorial
Created: Object #24.
```

Output: the thing goes into your inventory. Write down the number you actually received.

In every example below, replace `<hello>` with that complete dbref, including `#`. `<hello>` is a placeholder, not SharpMUSH syntax.

```
> examine <hello>
Hello Tutorial(#24Tn)
Type: THING Flags: NO_COMMAND
Owner: Alice(#21PenAc)  Zone: *NOTHING*
...
Home: Room Zero(#0R)
Location: Alice(#21PenAc)
```

Output: the name, owner, and location describe the thing you just created. The `n` after `T` is the `NO_COMMAND` flag, which `@create` sets on every new thing. While it is set, the game never checks the object for commands, so clear it:

```
> @set <hello>=!no_command
Hello Tutorial - NO_COMMAND reset.
```

## Write and run the command

Enter each of these lines separately:

```
> &CMD`HELLO <hello>=$+hello:@pemit/silent %#=Hello, %n!
Hello Tutorial/CMD`HELLO - Set.
> @set <hello>/CMD`HELLO=cmdsyntax
Hello Tutorial/CMD`HELLO - cmdsyntax set.
> +hello
Hello, Alice!
```

Output: the command answers only you, by name.

Here is what you wrote:

- ``&CMD`HELLO`` stores an attribute named ``CMD`HELLO``. The backtick groups related attribute names into a tree.
- `$+hello:` matches the command `+hello`. The part after the colon is its action list.
- `@pemit/silent` sends a private message without a confirmation to the sender.
- `%#` is the enactor, the character who used the command. `%n` is that character's name.
- `cmdsyntax` tells `examine` and the editor to lay the value out as a command list. It does not enable the command or grant any permission.

See [substitutions](/reference/sharpmush-help/substitutions/), [@pemit](/reference/sharpmush-help/pemit-command/) and [attribute flags](/reference/sharpmush-help/attribute-flags/#display-formatting).

**Store code with `&` when typing it at the terminal.** It stores the text as typed, for later execution. The attribute-setting form of `@set` evaluates its value first. See [evaluation order](/reference/sharpmush-help/evaluation-order/).

## Make one change and check it

Replace the same attribute:

```
> &CMD`HELLO <hello>=$+hello:@pemit/silent %#=Hello, %n! Your first softcode command is working.
Hello Tutorial/CMD`HELLO - Set.
> examine <hello>/CMD`HELLO
CMD`HELLO [#21x]:
$+hello:@pemit/silent %#=Hello, %n! Your first softcode command is working.
> +hello
Hello, Alice! Your first softcode command is working.
```

Output: `examine` shows the new value, and `x` after the owner's dbref is the `cmdsyntax` flag.

You can make this edit in the portal's softcode editor at `/softcode` instead. Select the object and the ``CMD`HELLO`` attribute, edit its value, and save. In the editor the value starts with `$+hello:`; do not paste the terminal's ``&CMD`HELLO <hello>=`` wrapper into it. Then run `+hello` in the terminal. Saving an attribute is a live database change.

## Understand who is running the code

There are three different identities to keep straight:

- **Owner:** who owns the code object.
- **Executor:** the object running this command, available as `%!` or `me` inside this action list.
- **Enactor:** the character who typed `+hello`, available as `%#`.

An object does not inherit its owner's roles. Creating it while logged in as an administrator does not make the object an administrator. Ownership and control still matter, so review both permissions and ownership when code later starts changing data. See [roles](/reference/sharpmush-help/roles/).

This greeting needs no privileged role on the object. If a later command performs a staff action, check the enactor's permission before doing the work. A check of `permission(me,...)` asks about the code object, not the player requesting the action.

## Add a small input contract

Let people choose between two greeting styles. Keep the original `+hello` command and add a separate attribute for the form with an argument:

```
> &CMD`HELLOSTYLE <hello>=$+hello *:@assert member(friendly formal,lcstr(trim(%0)))=@pemit/silent %#=Choose a style: +hello friendly or +hello formal.; @pemit/silent %#=if(strmatch(lcstr(trim(%0)),formal),Good day %n.,Hello %n!)
Hello Tutorial/CMD`HELLOSTYLE - Set.
> @set <hello>/CMD`HELLOSTYLE=cmdsyntax
Hello Tutorial/CMD`HELLOSTYLE - cmdsyntax set.
```

The long attribute-setting line is one terminal command. Visual wrapping is fine; do not insert a newline in the middle when pasting it.

The `*` captures the argument into `%0`. `trim()` removes surrounding spaces, `lcstr()` lowers its case, and `member()` permits exactly one of the two listed styles. If the check fails, `@assert` prints the usage message and stops the action list, so no greeting follows. On success, `if()` chooses the response. The semicolon separates the two stored commands. See [$-commands](/reference/sharpmush-help/commands/#patterns-and-registers) and [@assert](/reference/sharpmush-help/break-command/).

Treat captured input as data. Do not add `s()`, evaluate player-written attributes with `u()`, or otherwise evaluate the input again.

## Test the behavior you promised

Run these tests after your last edit:

| Input | Output |
| --- | --- |
| `+hello` | `Hello, Alice! Your first softcode command is working.` |
| `+hello friendly` | `Hello Alice!` |
| `+hello FORMAL` | `Good day Alice.` |
| `+hello pineapple` | `Choose a style: +hello friendly or +hello formal.` |
| `+hello formal extra` | `Choose a style: +hello friendly or +hello formal.` |
| `+hello 0` | `Choose a style: +hello friendly or +hello formal.` |
| `+hello formal; @emit SHOULD_NOT_RUN` | `Choose a style: +hello friendly or +hello formal.` and nobody in the room sees `SHOULD_NOT_RUN` |

For the last test, use a terminal without a client-side semicolon macro. SharpMUSH treats a line a player types as one command, so the semicolon stays part of the invalid style argument. Semicolons in a stored action list separate commands. See [action lists](/reference/sharpmush-help/action-lists/).

Then test with an ordinary player on a **separate non-staff account**. Another character on your admin account receives that account's roles. Check the test player's effective roles first. In these examples the second player is Bob.

1. With the thing still in your inventory, Bob cannot reach its `+hello`:

   ```
   > +hello
   Huh?  (Type "help" for help.)
   ```

2. In an approved test room, put the thing on the floor and check where it is. Use a room without an automatic DROP-TO, and respect its drop and take locks:

   ```
   > drop <hello>
   You drop Hello Tutorial.
   > think loc(<hello>)
   #23
   ```

   Output: `#23` is the test room. Bob can now run both forms, and the replies use his name:

   ```
   > +hello
   Hello, Bob! Your first softcode command is working.
   > +hello formal
   Good day Bob.
   ```

3. Repeat the invalid-input tests as Bob. Check that you, standing in the same room, see none of his greetings or usage messages.
4. Take the thing back with `get <hello>` and check that Bob's `+hello` answers `Huh?` again.

This checks reachability and real player behavior, which an admin test alone cannot. A game with another matching `+hello` may produce more output; isolate the tutorial or choose a unique command name if needed.

## Diagnose a missing response

Check these in order before changing privileges:

1. Did ``examine <hello>/CMD`HELLO`` show the attribute you intended to save?
2. Is the thing still in your inventory or in the same room?
3. Does it have `HALT` or `NO_COMMAND` set? A new thing has `NO_COMMAND`.
4. Can the enactor pass its use and command locks? A failed lock answers `Huh?  (Type "help" for help.)`, as if no command matched.
5. Is another command matching the same input?
6. Is the recipient `HAVEN`, or does their page lock refuse the object? Then the command runs but the private message is dropped, and the player sees nothing.

If code is running but no player sees the result, remember that `think` inside object code sends to the executor, the object itself; this guide uses `@pemit %#` to reach the enactor. Do not make the object a wizard to hide a matching, lock, or recipient problem. See [@pemit](/reference/sharpmush-help/pemit-command/).

## Save your work and stop cleanly

Export a readable copy before cleanup:

```
> @decompile <hello>
@create Hello Tutorial
&CMD Hello Tutorial=
&CMD`HELLO Hello Tutorial=$+hello:@pemit/silent %#=Hello, %n! Your first softcode command is working.
@set Hello Tutorial/CMD`HELLO=cmdsyntax
&CMD`HELLOSTYLE Hello Tutorial=$+hello *:@assert member(friendly formal,lcstr(trim(%0)))=@pemit/silent %#=Choose a style: +hello friendly or +hello formal.; @pemit/silent %#=if(strmatch(lcstr(trim(%0)),formal),Good day %n.,Hello %n!)
@set Hello Tutorial/CMD`HELLOSTYLE=cmdsyntax
```

Output: commands that rebuild the object. `&CMD` creates the empty branch that holds the two command attributes. Save the output with your version and test notes. Review its references before replaying it elsewhere; a decompile is a script that rebuilds the object, not an identity that carries between games. See [@decompile](/reference/sharpmush-help/decompile-command/).

When you later want to share the feature as a package, start with the read-only scan. It needs the `packages.admin` permission:

```
> @package/scan <hello>
PACKAGE SCAN: 1 object(s) selected.
  Hello Tutorial (THING, #24:1794355644062) -> ref 'hello_tutorial'; 3 visible attr(s), 1 flag(s).
Self-contained: no external dbrefs. Ready to package with:
  @package #24=<package-id>
```

Output: `#24:1794355644062` is the dbref with its creation time, so it names this object only. The object refers to no other dbref, so it can be packaged as it is. Without the permission the scan answers `Permission denied. You need the packages.admin permission.` Review any external references the scan lists before exporting with `@package` or the portal's `/admin/packages/author`. See [packages](/guides/packages/).

To keep the object but remove this lesson's commands, clear each attribute and then the empty branch:

```
> &CMD`HELLO <hello>
Hello Tutorial/CMD`HELLO - Cleared.
> &CMD`HELLOSTYLE <hello>
Hello Tutorial/CMD`HELLOSTYLE - Cleared.
> &CMD <hello>
Hello Tutorial/CMD - Cleared.
```

There is no equals sign: `&` with no value clears the attribute. Examine the object again and check the commands are gone.

If you are done with the whole object, first confirm its dbref and saved export, then destroy it. The first `@destroy` only marks it; a second destroys it at once:

```
> @destroy <hello>
Hello Tutorial(#24T) is scheduled to be destroyed.
> @destroy <hello>
Halted: Hello Tutorial(#24)
Destroyed.
```

See [@destroy](/reference/sharpmush-help/destroy-command/).

Your first command is complete when you can explain its scope, identify who runs it, show its valid and invalid outputs, and rebuild it from saved source. Build the next feature with the same loop: one change, explicit behavior, ordinary-player tests, and an export you can review.
