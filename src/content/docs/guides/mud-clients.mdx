A MUD client such as **Mudlet** can do more than show the game's text. Told where the player is, it
draws a map; told their health, it draws a gauge; told the channel lines, it keeps them in a window of
their own. The game tells it these things over **GMCP**, beside the text.

SharpMUSH handles GMCP itself: it agrees to it with each client, remembers what the client asked for,
and plays sounds. What the game tells a client about its rooms, channels and characters comes from
softcode packages, because only the game knows what a room's area or a character's health is. The
**MUD kit** is a set of those packages, ready to install.

## How it works

![A MUD client talks GMCP to the socket server, which keeps the client's Core.Supports list and passes it, and what the client sends, to the engine. The engine raises events, the MUD kit packages answer them with oob() and supported, and the engine sends the result back to the client. The rendering worker turns sound() and music() into Client.Media frames sent just before their line.](../../../assets/guide/mud-clients-flow.svg)

- **The socket server** agrees to GMCP with each telnet client and keeps the list of modules the client
  asked for. It sends `Client.Media.Default` when the game has a `media_base_url`.
- **The engine** keeps that list for [`gmcpsupports()`](#gmcpsupports), raises events such as
  ``OBJECT`MOVE``, ``ATTRIBUTE`CHANGE`` and ``SOCKET`GMCP``, and sends whatever softcode hands to
  [`oob()`](#oob-with-supported).
- **The packages** hear those events on the event handler, shape the game's data into the standard
  GMCP messages, and send them with `oob(..., supported)`.
- **The rendering worker** turns `sound()`, `music()` and `stopsound()` in a line into
  `Client.Media` messages, which the socket server sends just before the line.

## What GMCP is

GMCP is a telnet option. When a client connects, the game offers it and the client agrees. From then on
either side can send a **message**: a package name, such as `Room.Info`, and a body in JSON.

```
Room.Info {"num":26,"name":"Garden","area":"Town","environment":"garden","exits":{"south":0},"coords":"3,4,0"}
```

A client can say which modules it wants with `Core.Supports.Set`, a list of module names each with a
version, and add or remove modules later with `Core.Supports.Add` and `Core.Supports.Remove`. A module
covers everything under it: `Room` covers `Room.Info` and `Room.Players`.

What each client sends:

| Client | `Core.Supports` | What the MUD kit sends it |
|---|---|---|
| **Mudlet** | `Char 1`, `Char.Skills 1`, `Char.Items 1`, `Room 1`, `IRE.Rift 1`, `IRE.Composer 1`, `External.Discord 1`, `Client.Media 1` | Room, Char, Char.Items, External.Discord and Client.Media. Not Comm or Client, which Mudlet does not list: see [below](#when-mudlet-does-not-list-a-module) |
| **Blightmud**, **TinTin++**, **MUSHclient** | none, unless a script sends one | everything |
| **The web portal** | not used | everything sent with `oob()` |

An empty list means the client **never said**, not that it wants nothing, so a client that lists
nothing is sent everything. A client that sent a list is sent only what is on it.

### When Mudlet does not list a module

Stock Mudlet does not list `Comm` or `Client`, so it is not sent channel lines (`Comm.Channel.Text`),
its channel list, the game's interface package (`Client.GUI`) or its map (`Client.Map`). A Mudlet
script adds them:

```lua
sendGMCP([[Core.Supports.Add ["Comm.Channel 1", "Client 1"] ]])
```

A game's own Mudlet interface package can carry that line. For the very first offer, before any
interface is installed, a player can send it themselves and then type `+gui on`:

```
>> Core.Supports.Add ["Comm.Channel 1", "Client 1"]
> +gui on
<< Client.GUI {"version":"1.0","url":"https://example.org/game.mpackage"}
[GUI] Done: Your client will be offered the game's interface when you connect. It was offered it just now.
```

Here `>>` is a GMCP message the client sent, `<<` one the game sent, and `>` a command typed in the game.

## Installing the MUD kit

The MUD kit is bundled with the server but not installed until you choose it. Install it from the
portal's Packages page, from the **bundled** catalogue:

| Package | Sends |
|---|---|
| `gmcp-room` | `Room.Info`, `Room.Players`, `Room.AddPlayer`, `Room.RemovePlayer` |
| `gmcp-comm` | `Comm.Channel.Text`, `Comm.Channel.List` |
| `gmcp-items` | `Char.Items.List`, `Char.Items.Add`, `Char.Items.Remove` |
| `gmcp-char` | `Char.Name`, `Char.Vitals`, `Char.Status` |
| `mudlet-client` | `Client.GUI`, `Client.Map`, `External.Discord.Info`, `External.Discord.Status`, and `+gui` |
| `mud-kit` | nothing itself: it installs the five above and adds the `+help gmcp` overview |

Each of the five installs and uninstalls on its own, so a game takes only what it uses. They need
`plus-help` and `plus-config`, which are installed with them. Every package adds its handlers to the
event handler (`#9` in a new game) one level below the event, such as ``OBJECT`MOVE`GMCPROOM``, beside
the handlers already there. See [Events](/guides/events/#several-attributes-on-one-event).

Staff change each package's settings with `+config`, for example `+config gmcp-room`:

```
> +config mudlet-client/gui-url=https://example.org/game.mpackage
[CONFIG] Done: mudlet-client/gui-url is now https://example.org/game.mpackage, was none.
```

Players read about it with `+help gmcp`.

<Aside>
A client whose player turned on screen reader mode is sent chat lines without colour, and `+gui` answers
in sentences instead of a box. See [Screen Readers](/guides/screen-readers/).
</Aside>

## The packages

Each message below is listed with its fields and when it is sent. The examples are what a client was
sent on a running server.

### gmcp-room: the map and who is here

| Message | Sent |
|---|---|
| `Room.Info` | to a player when they move, and on each new connection |
| `Room.Players` | with every `Room.Info` |
| `Room.AddPlayer` | to the others in the room, when a connected player arrives, or connects for the first time |
| `Room.RemovePlayer` | to the others in the room, when a player leaves, or their last connection closes |

```
Room.Info {"num":26,"name":"Garden","area":"Town","environment":"garden","exits":{"south":0},"coords":"3,4,0"}
Room.Players [{"name":"Wren","fullname":"Wren of the Marsh"}]
Room.AddPlayer {"name":"Tam","fullname":"Tam"}
Room.RemovePlayer "Wren"
```

`Room.Info`:

| Field | Type | What |
|---|---|---|
| `num` | number | the room's dbref number. It never changes while the room exists, which is what a mapper wants |
| `name` | string | the room's name |
| `area` | string | the room's `AREA` attribute, or else the name of its zone, or else empty |
| `environment` | string | the room's `ENVIRONMENT` attribute, such as `garden`, or empty |
| `exits` | object | each exit the player sees, by name, to the number of the room it leads to. This is [`exitmap()`](#exitmap) |
| `coords` | string | `x,y,z` from the room's `X`, `Y` and `Z` attributes, a missing one as `0`. Left out of a room with none of them, or with one that is not a number |

`Room.Players` is a list of every connected player in the room the viewer sees, the viewer included. A
DARK player is seen only by themself and by someone who may see everything. Each entry, like the body of
`Room.AddPlayer`, is:

| Field | Type | What |
|---|---|---|
| `name` | string | the player's name |
| `fullname` | string | the player's `FULLNAME` attribute, or else their name |

`Room.RemovePlayer` is the player's name, as a string.

Settings, `+config gmcp-room`:

| Setting | Default | What |
|---|---|---|
| `area` | `AREA` | the room attribute naming its area. A room without it is in its zone's area. Empty uses the zone alone |
| `environment` | `ENVIRONMENT` | the room attribute holding its terrain. Empty sends none |
| `coordinates` | `X Y Z` | the room attributes holding x, y and z, in that order (two or three) |
| `fullname` | `FULLNAME` | the player attribute holding the name shown in full |

To place a room on a mapper, set its attributes:

```
> &AREA #26=Town
Garden/AREA - Set.
> &ENVIRONMENT #26=garden
Garden/ENVIRONMENT - Set.
> &X #26=3
Garden/X - Set.
> &Y #26=4
Garden/Y - Set.
> &Z #26=0
Garden/Z - Set.
```

### gmcp-comm: channels and pages

| Message | Sent |
|---|---|
| `Comm.Channel.Text` | a channel line or a page reached the player |
| `Comm.Channel.List` | the player connects, joins or leaves a channel |

```
Comm.Channel.List [{"name":"MudKit","caption":"MudKit","command":"+mudkit"}]
Comm.Channel.Text {"channel":"MudKit","talker":"Alice","text":"<MudKit> Alice says, "Hello, Bob.""}
Comm.Channel.Text {"channel":"page","talker":"Alice","text":"Alice pages: Over here."}
Comm.Channel.Text {"channel":"page","talker":"Alice","text":"You paged Bob with 'Over here.'"}
```

The `<` and `"` are JSON's way of writing `<` and `"`; a client reads them as those characters.

`Comm.Channel.Text`:

| Field | Type | What |
|---|---|---|
| `channel` | string | the channel's name. A page is filed under `page` |
| `talker` | string | who spoke, without colour |
| `text` | string | the whole line as the player's screen shows it, in ANSI colour, or without colour for a screen reader |

A page is sent to each player it reached, as they see it (`Alice pages: Over here.`), and to the pager,
as they see it (`You paged Bob with 'Over here.'`). The engine names exactly who received each line, so
nobody is sent a line they did not see.

`Comm.Channel.List` is a list of the channels the player is on, each:

| Field | Type | What |
|---|---|---|
| `name` | string | the channel's name |
| `caption` | string | the same name, for the client to show |
| `command` | string | what a client types before a message to speak on the channel: `+` and the name in lower case |

Settings, `+config gmcp-comm`:

| Setting | Default | What |
|---|---|---|
| `pages` | on | whether pages are sent too |
| `page-channel` | `page` | the channel name pages are filed under |

Stock Mudlet does not list `Comm`: see [When Mudlet does not list a module](#when-mudlet-does-not-list-a-module).

### gmcp-items: the inventory window

| Message | Sent |
|---|---|
| `Char.Items.List` | on connect (both lists), when the client asks, and the room's list when the player moves |
| `Char.Items.Add` | a thing reached the player's hands or their room |
| `Char.Items.Remove` | a thing left them |

A client asks by sending `Char.Items.Inv` or `Char.Items.Room`, with no body, and the answer goes to the
connection that asked.

Alice is handed a lantern, then drops it. Bob is in the room:

```
Alice << Char.Items.Add {"location":"inv","item":{"id":"29","name":"Lantern"}}
Alice << Char.Items.Remove {"location":"inv","item":{"id":"29","name":"Lantern"}}
Alice << Char.Items.Add {"location":"room","item":{"id":"29","name":"Lantern"}}
Bob   << Char.Items.Add {"location":"room","item":{"id":"29","name":"Lantern"}}
Alice >> Char.Items.Inv
Alice << Char.Items.List {"location":"inv","items":[]}
```

| Field | Type | What |
|---|---|---|
| `location` | string | `inv`, what the player carries, or `room`, what lies in their room |
| `items` (List) | list | every thing there the player sees |
| `item` (Add, Remove) | object | the thing that came or went |
| `id` | string | the thing's dbref number, as digits |
| `name` | string | the thing's name |

Things only: players are in `Room.Players` and exits in `Room.Info`. A DARK thing in a room is listed
only to a player who may see everything. What is inside a container is not sent.

Settings, `+config gmcp-items`:

| Setting | Default | What |
|---|---|---|
| `room` | on | whether the room's things are sent, or only what the player carries |

### gmcp-char: name, gauges and status

| Message | Sent |
|---|---|
| `Char.Name` | on connect, and when the player is renamed |
| `Char.Vitals` | on connect, and when a vitals attribute changes |
| `Char.Status` | on connect, when a status attribute changes, and on a rename |

With `+config gmcp-char/status=LEVEL`, Wren connects:

```
Char.Name {"name":"Wren","fullname":"Wren of the Marsh"}
Char.Vitals {"hp":25,"maxhp":40}
Char.Status {"name":"Wren","fullname":"Wren of the Marsh","level":3}
```

`Char.Name` has `name` and `fullname`, as in `Room.Players`. `Char.Vitals` has one field for each
vitals attribute the player has, and `Char.Status` the player's `name` and `fullname` and then one field
for each status attribute. Each field is named after the attribute's last name in lower case
(``STATS`HP`` is `hp`), and its value is a number when the attribute holds one, else a string. An
attribute the player does not have is left out, so a player with none is sent `Char.Vitals {}`. Mudlet's
gauges read `hp` and `maxhp`, `mp` and `maxmp`, `mv` and `maxmv`.

Settings, `+config gmcp-char`:

| Setting | Default | What |
|---|---|---|
| `vitals` | `HP MAXHP MP MAXMP` | the player attributes sent as `Char.Vitals` |
| `status` | none | the player attributes sent as `Char.Status`, such as `LEVEL CLASS` |
| `fullname` | `FULLNAME` | the player attribute holding the name shown in full |
| `watch-new` | on | whether every new copy of a vitals or status attribute is made watched, with `@attribute/access` |

The package sends a change the moment it happens, without checking anyone's attributes over and over.
That is what [watched attributes](#watched-attributes) are for.

### mudlet-client: the game's interface, map and Discord

| Message | Sent |
|---|---|
| `Client.Map` | when Mudlet says `Core.Hello` |
| `Client.GUI` | when the player connects, unless they turned `+gui off`; on `Core.Hello` from a connection already logged in; on `+gui on` |
| `External.Discord.Info` | when Mudlet says `External.Discord.Hello` |
| `External.Discord.Status` | on `External.Discord.Hello` and `External.Discord.Get`, and when the player connects |

```
Client.Map {"url":"https://example.org/map.xml"}
Client.GUI {"version":"2.1","url":"https://example.org/game.mpackage"}
External.Discord.Info {"inviteurl":"https://discord.gg/example"}
External.Discord.Status {"game":"SharpMUSH","details":"Playing Wren","starttime":1792050984}
```

| Message | Field | What |
|---|---|---|
| `Client.GUI` | `version` | the interface package's version. Mudlet installs it again when this changes |
| | `url` | where Mudlet downloads the interface package (`.mpackage`) |
| `Client.Map` | `url` | where Mudlet downloads the game's map |
| `External.Discord.Info` | `inviteurl` | an invite to the game's Discord server; left out when not set |
| | `applicationid` | the game's own Discord application id; left out when not set |
| `External.Discord.Status` | `game` | the game's name |
| | `details` | `Playing` and the character's name; left out before login, or when `discord-character` is off |
| | `starttime` | when the player connected, in seconds since 1970; left out before login |

A setting left empty sends nothing: no `Client.GUI` without a `gui-url`, no `Client.Map` without a
`map-url`.

Settings, `+config mudlet-client`:

| Setting | Default | What |
|---|---|---|
| `gui-url` | none | the interface package Mudlet downloads |
| `gui-version` | `1.0` | its version; change it with each new package |
| `map-url` | none | the map Mudlet downloads |
| `discord-invite` | none | an invite to the game's Discord server |
| `discord-application` | none | the game's own Discord application id |
| `discord-game` | the game's name | the game's name in a Discord status |
| `discord-character` | on | whether the status names the character played |

Players choose whether they are offered the interface:

| Command | What |
|---|---|
| `+gui` | whether the game has an interface package, its version, and whether it is offered to you |
| `+gui on` | offer it when you connect, and offer it now |
| `+gui off` | stop offering it |

```
> +gui off
[GUI] Done: Your client will not be offered the game's interface when you connect. +gui on offers it again.
> +gui
╔════════════════════════════╡ Mudlet interface ╞════════════════════════════╗
║ Package: https://example.org/game.mpackage                                 ║
║ Version: 2.1                                                               ║
║ Offered: no, you turned it off                                             ║
║ Map:     https://example.org/map.xml                                       ║
╠════════════════════════════════════════════════════════════════════════════╣
║ +gui on and +gui off choose whether it is offered.                         ║
╚════════════════════════════════════════════════════════════════════════════╝
```

Stock Mudlet does not list `Client`, so it is sent neither `Client.GUI` nor `Client.Map` until a script
adds it: see [When Mudlet does not list a module](#when-mudlet-does-not-list-a-module).

## Watched attributes

A gauge has to change the moment the health behind it does. Rather than read every player's attributes
over and over, the game says when one changes, but only for an attribute flagged **`watched`**, so
attributes nobody watches cost nothing.

- `@set <object>/<attribute>=watched` watches one attribute on one object.
- `@attribute/access <attribute>=watched` makes every copy of a standard attribute created from then on
  watched. Copies that already exist keep their own flags. This replaces the attribute's default flags,
  so a game whose attribute already has default flags names them too.

Each change to a watched attribute raises the ``ATTRIBUTE`CHANGE`` event on the event handler, with
`objid`, `attribute` (its full name in upper case), `old`, `new` and `enactor`. See the
[event list](/reference/sharpmush-help/sharpevents/).

gmcp-char watches the attributes its `vitals` and `status` settings name, for you:

- on every player who already has one, when it is installed and whenever those settings change;
- on each player as they connect, which catches a copy made before it was watched;
- with `@attribute/access`, on every new copy, while `watch-new` is on. Turning `watch-new` off, or
  dropping an attribute from `vitals` or `status`, puts the default the package gave back to none.

So a staff member or a combat system only sets the attribute, and the player's client is told:

```
> &MAXHP *Alice=50
Alice/MAXHP - Set.
Alice << Char.Vitals {"maxhp":50}
> &HP *Alice=35
Alice/HP - Set.
Alice << Char.Vitals {"hp":35,"maxhp":50}
```

Each message carries the whole gauge, not only the attribute that changed.

## Sounds and music

`sound()`, `music()` and `stopsound()` already play in MXP and Pueblo clients and in the web portal. A
client that lists `Client.Media` in `Core.Supports`, as Mudlet does, is sent a GMCP message for each,
just before the line they ride in:

```
> @pemit/list [pmatch(Wren)] [pmatch(Tam)]=[sound(door.wav,80)]The door creaks open.
Wren << Client.Media.Play {"name":"door.wav","type":"sound","volume":80}
Wren << The door creaks open.
Tam  << The door creaks open.
> @pemit *Wren=[music(theme.ogg,50,-1)]Music starts.
Wren << Client.Media.Play {"name":"theme.ogg","type":"music","volume":50,"loops":-1,"continue":false,"key":"music"}
> @pemit *Wren=[sound(https://cdn.example.org/fx/bell.wav)]A bell rings.
Wren << Client.Media.Play {"name":"bell.wav","url":"https://cdn.example.org/fx/","type":"sound"}
> @pemit *Wren=[stopsound(music)]The music stops.
Wren << Client.Media.Stop {"type":"music"}
> @pemit *Wren=[stopsound()]Silence.
Wren << Client.Media.Stop {}
```

Tam's client listed nothing, so it was sent the line and no sound.

`Client.Media.Play`:

| Field | What |
|---|---|
| `name` | the file to play |
| `url` | for a full web address, the directory it is in; left out for a file name, which the client fetches from `Client.Media.Default` |
| `type` | `sound`, or `music` for `music()` |
| `volume` | 0 to 100, when given |
| `loops` | how many times to play, when given; `-1` plays until stopped |
| `continue`, `key` | music only: `key` is `music`, so a new piece replaces the one playing |

`Client.Media.Stop` has `type` `sound` or `music` for `stopsound(effects)` or `stopsound(music)`, and no
fields for `stopsound()`, which stops everything.

`sound()`, `music()` and `stopsound()` need a wizard or the `Send_OOB` power.

### media_base_url

When `sound()` names a file rather than a full address, the client needs to know where the game keeps
its sounds. Set `media_base_url`:

```
> @config/set media_base_url=https://example.org/sounds
Option set.
```

Every client that agrees to GMCP is then sent `Client.Media.Default` as it connects, before the login
screen, and again whenever the setting changes. A `/` is added when the address does not end in one:

```
<< Client.Media.Default {"url":"https://example.org/sounds/"}
```

Empty sends nothing, and the game's sounds then need full addresses. It can also be set in `mush.cnf`.

## Functions for GMCP softcode

The MUD kit is ordinary softcode, built on three functions. Use them to send packages of your own.

### gmcpsupports()

`gmcpsupports(<descriptor|player>[, <package>])` returns the list a client sent in `Core.Supports`, or,
given a package, `1` when the client listed it or a module it belongs to and `0` otherwise. Names match
without regard to case.

```
> think gmcpsupports(me)
Char 1 Char.Skills 1 Char.Items 1 Room 1 IRE.Rift 1 IRE.Composer 1 External.Discord 1 Client.Media 1
> think gmcpsupports(me, Room.Info)
1
> think gmcpsupports(me, Comm.Channel)
0
```

A client that listed nothing returns an empty list, and `0` for every package:

```
> think strlen(gmcpsupports(me))
0
> think gmcpsupports(me, Room.Info)
0
```

A player name reads that player's least idle connection. Reading anyone else's connections needs a
wizard or the `Send_OOB` power.

### oob() with supported

`oob(<players>, <package>[, <message>[, supported]])` sends a GMCP message and returns how many
connections took it. With the fourth argument `supported`, a telnet client is sent the message only
when it listed the package or a module it belongs to, or listed nothing at all. Without it, every client
that agreed to GMCP is sent it. A portal connection always is.

Wren's stock Mudlet did not list `Comm`:

```
> think oob(me, Comm.Channel.Text, json(object, channel, json(string, test)), supported)
0
> think oob(me, Comm.Channel.Text, json(object, channel, json(string, test)))
<< Comm.Channel.Text {"channel":"test"}
1
```

Every MUD kit package sends with `supported`. Use it for your own packages too, rather than testing
`gmcpsupports()` first. Sending to anyone but yourself needs a wizard or the `Send_OOB` power. A
descriptor number sends to that one connection, even before anyone has logged in on it, which is how a
``SOCKET`GMCP`` handler answers what a client asked.

### exitmap()

`exitmap(<room>[, <viewer>])` returns the exits in a room as a JSON object, each exit's name to the
number of the room it leads to: the `exits` of `Room.Info`.

```
> think exitmap(here)
{"north":26}
```

Only the exits the viewer can see are listed, the ones `look` would show them. Each is named up to its
first `;`, so `north;n` is `north`; when two exits share a name, the first is kept. An exit to HOME leads
to the viewer's own home, a variable exit is `-2`, and an unlinked exit is `-1`. You may map a room you
can examine or are standing in.

## A worked Mudlet session

Two players connect to a game with the MUD kit installed. **Wren** plays in a stock Mudlet 4.19 and
**Tam** in a client that agrees to GMCP and lists nothing, as TinTin++ does. Staff have set:

```
> +config mudlet-client/gui-url=https://example.org/game.mpackage
> +config mudlet-client/map-url=https://example.org/map.xml
> +config mudlet-client/discord-invite=https://discord.gg/example
> +config gmcp-char/status=LEVEL
> @config/set media_base_url=https://example.org/sounds
```

Wren has `FULLNAME` `Wren of the Marsh`, `LEVEL` 3, `MAXHP` 40 and `HP` 25. North of Room Zero is a
Garden in the area `Town`, with terrain `garden` and coordinates 3, 4, 0.

<Steps>

1. **Wren connects.** The game offers GMCP, Mudlet agrees, and is sent where the game's sounds are. Mudlet
   says hello and lists its modules, and Wren logs in:

   ```
   << Client.Media.Default {"url":"https://example.org/sounds/"}
   >> Core.Hello {"client": "Mudlet", "version": "4.19.1"}
   >> Core.Supports.Set ["Char 1", "Char.Skills 1", "Char.Items 1", "Room 1", "IRE.Rift 1", "IRE.Composer 1", "External.Discord 1", "Client.Media 1"]
   << Char.Name {"name":"Wren","fullname":"Wren of the Marsh"}
   << Char.Vitals {"hp":25,"maxhp":40}
   << Char.Status {"name":"Wren","fullname":"Wren of the Marsh","level":3}
   << Char.Items.List {"location":"inv","items":[]}
   ```

   next channel line also goes to Mudlet's chat window, and `+gui on` offers the interface:

   ```

   > +gui on
   << Client.GUI {"version":"1.0","url":"https://example.org/game.mpackage"}
   ```

   is told Tam arrived:

   ```
   Tam  << Room.Players [{"name":"Wren","fullname":"Wren of the Marsh"},{"name":"Tam","fullname":"Tam"}]
   Wren << Room.AddPlayer {"name":"Tam","fullname":"Tam"}
   Tam  << Client.GUI {"version":"1.0","url":"https://example.org/game.mpackage"}
   Tam  << Comm.Channel.List []
   ```

   ```
   > &HP *Wren=20
   Wren << Char.Vitals {"hp":20,"maxhp":40}
   > &LEVEL *Wren=4
   Wren << Char.Status {"name":"Wren","fullname":"Wren of the Marsh","level":4}
   ```

6. **A door creaks.** Wren's Mudlet plays `https://example.org/sounds/door.wav`; Tam sees the line alone,
   as shown in [Sounds and music](#sounds-and-music).
